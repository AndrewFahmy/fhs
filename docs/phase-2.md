# Phase 2 — FHS

> Status: **planned, nothing built.** v1 is complete — the kernel, the foundation, seventeen endpoints
> across all five domain concepts, seven architecture tests, a 65-test integration suite, and a React SPA
> covering every screen the API can serve. Phase 2 is the first work that is not about proving Chain
> Composition holds up.
>
> `chain-composition.md` said its successor would be *"a new document written incrementally against this
> one."* This is that document. It does **not** restate the kernel, the rules or the slice anatomy —
> `chain-composition.md` remains canonical for all of it, and every workstream below is expected to obey it.
> What lives here is scope, sequencing, and the decisions phase 2 forces that v1 never had to make.
>
> **§2 is the ledger of what is actually agreed.** Read it first. Settled so far: the demo dataset and how
> it is generated (§4), and the `Facility` concept with read-level scoping (§10). Everything marked
> *proposed* is a recommendation carrying a rationale, not an agreement, and everything under *open* still
> blocks something. It should be the first thing updated as decisions land.

## 1. What phase 2 is

Six workstreams. **The letters are labels, not an order** — §3 argues the sequence, and it is not
alphabetical.

| | Workstream | One line |
| --- | --- | --- |
| **A** | Demo dataset and the read path at scale | 25M defects + 25M escapes, and making the read side survive them |
| **B** | Edit, delete and reactivation | The mutations v1 deliberately omitted |
| **C** | Escape attribution | Reversing a v1 domain decision, carefully |
| **D** | Analytics and the dashboard | The landing page that has been an empty component since 2026-09-12 |
| **E** | Caching | `HybridCache` over the three lookups |
| **F** | Facilities and scoped administration | A new domain concept, a second admin role, and the first authorization that depends on data |

**What phase 2 is not.** It is not a second architecture. No workstream below needs a kernel change, and
only one needs an architecture *rule* change (§9). Nothing in `chain-composition.md` §14 is being pulled
forward: if a step starts to feel like it needs `.OnCommitted<>()` or a conditional link, that is a §13
signal, not a licence.

It is also not an implementation plan in the sense of code. Per the working agreement the developer writes
every line by hand, one presented step at a time, and the project is run once at the end. §12 is the step
list; the snippets in this document are illustrative shapes, not the steps.

## 3. The ordering, and why

The six workstreams are not independent, and the dependencies run in one direction.

**A comes first because it changes the ground everything else stands on.** Indexes, paging semantics and
the dataset are what turn "the read side works" into "the read side works at scale." Analytics queries are
written against that dataset; caching decisions are only measurable against it; the edit endpoints run
migrations against it. Doing A last means doing the other five twice.

**C and F are inside A's window, not after it.** Attribution adds columns to `escapes`; facilities add a table,
a required foreign key on `stations`, and — if facility scope restricts reading — a denormalised `FacilityId` on
`defects`. Adding a nullable column to a large table is cheap, but indexing or backfilling one is not, and
a *required* foreign key on a populated table is worse. So both schema decisions have to land before the
generator runs, even though the feature work around them can come later.

**F is the largest of the six and the least contained.** It introduces the first authorization that depends
on the row being touched rather than on the route, which no v1 endpoint does. Its schema half is urgent;
its feature half can follow B.

**B comes before D** because edit and delete change what a record *is*. An analytics layer built on the
assumption that defects are append-only will quietly acquire bugs the first time a record is corrected.

**E comes last, deliberately.** Caching is the only workstream whose value is measurable rather than
assumed, and it cannot be measured before A exists. Building it first would mean caching queries whose cost
nobody has observed — and §8 argues that at least one of the obvious targets should not be cached at all.

```text
A (dataset, indexes, paging)  ──┬──►  B (edit/delete)  ──►  D (analytics)  ──►  E (caching)
                                │
   C schema ───────────────────┤   C feature work ────────────────────────►
   F schema ───────────────────┘   F feature work ──────────────►
   (both must land before the generator runs)
```

## 4. Workstream A — the demo dataset and the read path at scale

### 4.1 Why 50M and not 2B

The target is **50M fault rows in total: 25M defects and 25M escapes.** The original plan was 2B, generated
by a console app on Aspire startup. The arithmetic does not support it.

`Defect` and `Escape` rows are near-identical in size, roughly 220 bytes each: ~100 bytes of fixed columns
(four uuids, two timestamps, an enum), a ~28-byte tuple header, plus `Description` and a half-populated
`Resolution`.

| | 2B rows | 50M rows — 25M + 25M |
| --- | --- | --- |
| Heap | ~440 GB | ~11 GB across the two tables |
| Primary keys | ~70 GB | ~1.8 GB |
| Supporting indexes (§4.4, both tables) | ~300 GB+ | ~10 GB |
| **Total** | **~800 GB – 1 TB** | **~23 GB** |
| Generation, indexes dropped | hours, best case | minutes |
| Index builds afterward | hours each | minutes |
| Realistic first run | most of a day | a coffee |

The 2B figure also cannot be a startup step in any form. It is a deliberate, guarded, run-it-overnight job,
and any bug in the generator means running it again.

**Splitting 50M across two tables changes no recommendation in this workstream.** At 25M rows a table is
~5.5 GB, so a sequential scan still takes tens of seconds and missing indexes still hurt exactly as
instructively; `OFFSET 250000` is still pathological; an exact `COUNT` over a filtered set is still seconds
per request. Every pathology §4.4 and §4.5 address arrives well before 25M. What the split buys is that
`GET /escapes` is stressed as hard as `GET /defects`, rather than one read path being exercised and the
other assumed.

**One domain note, worth remembering rather than fixing.** A 1:1 ratio of escapes to defects is not what a
real facility looks like — an escape is a containment failure and should be far rarer. That is a deliberate
trade of plausibility for read-path coverage, and it surfaces again in §7.1 for any dashboard tile that
expresses escapes as a rate.

**If the target ever moves past ~100M**, the answer is `PARTITION BY RANGE (created_at)` on `defects` —
the same tool `chain-composition.md` already reaches for on the outbox — which makes generation, retention
and index maintenance tractable in a way that raw row count does not.

### 4.2 Storage stays on the bind mount

`AppHost.cs` uses `.WithDataBindMount("../../temp/db/")`, and **it stays** — decided 2026-09-12, against a
recommendation to switch to `.WithDataVolume()`.

The reason is POC hygiene, and it is a good one: every piece of container state — Postgres, pgAdmin,
Keycloak — lives under `temp/`, which makes the whole environment one folder to inspect and one gesture to
reset. Splitting Postgres out into a Docker-managed volume would trade that for throughput on a machine
where nothing is production.

**The argument against it was calibrated to a terabyte and mostly dissolves at ~23 GB.** A bind mount to a
Windows host path does go through Docker Desktop's filesystem translation layer, and Postgres' fsync-heavy
random I/O is close to its worst case for it — but the steady-state working set here is small, and the
penalty is only really felt during one event: the generation run in §4.3, which is the most write-intensive
thing this project will ever do.

Two mitigations for that window, neither of which touches the mount:

- **`synchronous_commit = off` for the load only.** It directly counteracts the fsync cost the bind mount
  imposes, and what it risks — losing the last few transactions on a crash — is meaningless for regenerable
  demo data. Set it per session in the generator so the API is unaffected.
- **A raised `max_wal_size` for the load window.** With two parallel writers (§4.3) doubling the write
  rate, checkpoint thrash is the likeliest thing to eat the gain from parallelism, and this is the cheapest
  way to avoid it.

**Trigger to revisit:** the generation run becoming slow enough that regenerating the dataset feels
expensive. The dataset's value depends on being cheap to throw away and rebuild; if that stops being true,
the mount is the first thing to change.

### 4.3 The generator

**It runs automatically under Aspire, in parallel with a live API.** Clone the repo, `aspire run`, and the
system comes up working and fills with data — no manual step, no interference. That property is the goal
and it constrains everything below; a faster offline loader that requires someone to know about it would
be the wrong trade.

| Property | Decision |
| --- | --- |
| Location | A new project outside `backend/` — it is a development tool, not part of the API |
| Trigger | Automatic, started by the AppHost on every run |
| Gate | `WaitFor(api)`, **not** `WaitFor(database)` — see below |
| Schema | **None.** The generator counts rows and writes data. Indexes and every other schema object are defined in the API's migrations |
| Guard | Idempotent, and load-bearing — see below |
| Insert path | `COPY` via Npgsql's binary importer, not EF. Orders of magnitude, not percentages |
| Indexes | **Stay in place throughout.** Not dropped and rebuilt |
| Concurrency | Defects and escapes written by two parallel writers |
| Realism | Bogus, used to build pools rather than per row |
| Determinism | A fixed seed, so the dataset is reproducible and a demo tells the same story twice |
| Progress | An OpenTelemetry counter, surfaced on the Aspire dashboard |

**`WaitFor(api)` is the schema gate.** `WaitFor(database)` only means Postgres is accepting connections;
the tables arrive later. `Program.cs` awaits `MigrateAsync()` *before* `app.Run()`, so the API does not
listen — and therefore does not report healthy — until migrations have completed. Waiting on the API
therefore waits on the schema, while leaving the API free to start and serve immediately. Nothing about the
parallelism is given up. Note the coupling: if §4.6 moves migration out of API startup, this gate moves
with it.

**The guard is not hygiene, it is load-bearing.** Automatic start on every run, plus a bind mount that
persists the data, means the second `aspire run` would cheerfully write another 50M rows on top of the
first. A row-count check is what stands between the repo and a database that doubles on every restart, and
it should be the first thing the generator does. It doubles as the schema check for free: querying
`defects` fails loudly if the table is not there.

**Indexes stay because two separate decisions require it.** The generator has no schema capability, and
queries cannot be served against unindexed tables while the load runs. The cost is real — every row
maintains roughly five indexes — and it is the correct price for a system that is live during generation.

**Bogus builds pools, not rows.** `Faker<T>` evaluates its rule set per property per row, and
`Lorem.Sentence()` is not cheap; calling it 50M times is minutes of CPU competing with the API for cores.
Use it where realism is visible and volume is small — all the reference data, plus a pool of perhaps
10–20k descriptions and resolutions — then compose the fact rows by sampling those pools with a plain RNG.
Nobody can tell that a description recurs across 25M rows, and the quality is identical where anyone looks.

One trap: Bogus' global `Randomizer.Seed` is **not thread-safe**, so a fixed seed plus parallel generation
silently stops being reproducible. Each writer needs its own seeded `Faker`.

**The distribution matters as much as the count.** A dataset of uniformly random rows makes every analytics
screen look like noise and hides the exact query pathologies the exercise is meant to expose:

- **Error codes Zipf-distributed, not uniform** — a top-N chart is meaningless when every code has 1/N of
  the volume, and a real taxonomy is heavily skewed.
- **~70% resolved**, so the `IsResolved` filter is selective in both directions and the partial index in
  §4.4 has something to do.
- **`created_at` spread across two to three years** with weekday and shift shape, so time bucketing and
  trend lines have structure rather than a flat line.
- **Reference data at realistic cardinality** — a handful of facilities, a few hundred stations spread across
  them, a few thousand error codes, tens of thousands of customers. These stay small no matter how many
  defects exist, and §8.4 turns on that fact.
- **Escapes at parity with defects — 25M each — by decision rather than realism** (§4.1). The split buys
  read-path coverage on both tables; it costs plausibility on anything that reads as an escape rate.

**Load order and direction both matter, because the app is live while this happens.**

*Reference data first, and the generator owns it.* Facilities, then stations bound to them, then error codes
and customers — seconds of work, and what every dropdown and every create form binds to. Seeding it before
the faults means the app is genuinely usable from the first moment instead of being an empty shell that
slowly fills, and it means **every environment starts from the same lookups**, which is the developer's
stated reason for putting reference data here rather than leaving it to whoever set the environment up.

*Then faults, newest first.* The default list is `created_at DESC`. Insert oldest-first and every batch
lands on page 1, churning the list continuously under whoever is looking at it. Insert newest-first and
page 1 stabilises within seconds while older rows fill in behind it. Same data, same duration — the
difference between a demo that looks alive and one that looks unstable.

*Actors are a prerequisite nobody expects.* `Defect.CreatedBy` and `Escape.ReportedBy` are foreign keys to
`Actor`, and `COPY` enforces foreign keys — nothing is skipped. In v1 an actor only ever comes into
existence through `ResolveActor` mapping a Keycloak subject, so the generator has to write synthetic actor
rows itself, with `SubjectId` values that cannot collide with a real Keycloak subject. Once workstream F
lands those actors also carry facility assignments (§10.2), and the seed should include both a system admin
and at least two facility admins — otherwise the role distinction cannot be demonstrated on a fresh clone.

The same applies to every other FK: generate the reference-data GUIDs client-side, insert them, keep the
arrays in memory and sample from them, so nothing needs reading back.

**`ANALYZE` periodically, or the indexes will appear not to work.** This is the failure mode most likely to
make the app look broken during a load. Postgres plans from table statistics, and a table that has just
gone from 0 to 25M rows has statistics saying it is empty until autovacuum catches up — which, under a
sustained bulk load, it will not. The planner will believe the table is tiny, choose nested loops and
sequential scans, and the carefully chosen indexes in §4.4 will go unused. Running `ANALYZE` on the fault
tables every few million rows costs almost nothing and prevents it. Each writer analyses its own table.

**Two writers means double the checkpoint pressure**, which is why §4.2's load-window settings gain
`max_wal_size` alongside `synchronous_commit = off`. Expect meaningful speedup from parallelism but not a
clean halving: WAL is a single serialized stream and the bind mount is the narrowest pipe in the setup, so
both writers contend for the same I/O.

**Progress belongs on the Aspire dashboard.** As an Aspire project resource the generator gets
ServiceDefaults and OTLP export, so a `System.Diagnostics.Metrics` counter incremented per batch appears as
a live graph in the Metrics tab — rows per second, which is more informative than a percentage, for about
five lines of code. A log line every N rows puts a readable percentage in the Console tab. Putting the
percentage on the resource row itself needs `ResourceNotificationService.PublishUpdateAsync`, which can
only be called from the AppHost — workable as a small polling loop there that reads the row count and
publishes the state text, and entirely optional.

### 4.4 Indexes

`DefectConfiguration` and `EscapeConfiguration` declare **no indexes at all** today. Every filter on
`GET /defects` is a sequential scan; the only reason this has never been felt is that the tables hold
test data.

`QueryDefects` filters on station code, error code, severity and resolved-state — each optional — and
sorts by `created_at DESC, id DESC`. A reasonable starting set:

| Index | Serves |
| --- | --- |
| `(created_at DESC, id DESC)` | The unfiltered default list, which is the most common request |
| `(station_id, created_at DESC)` | Station filter |
| `(error_code_id, created_at DESC)` | Error code filter |
| `(severity, created_at DESC)` | Severity filter |
| `(created_at DESC) WHERE resolved_at IS NULL` | Open defects — partial, small, and the case users actually live in |

Two caveats, both worth stating before anyone treats that table as the answer:

**Filters combine, and this set does not cover the combinations.** Postgres will bitmap-AND two of these,
which is usually good enough, but the honest position is that the final set is decided by
`EXPLAIN (ANALYZE, BUFFERS)` against the generated data, not by reasoning in a document. Start here,
measure, adjust.

**`Id` is a v7 GUID, so it correlates with `created_at`.** That makes a BRIN index on `created_at` unusually
effective for range scans, at a fraction of a btree's size — worth measuring against the analytics queries
in workstream D specifically, where wide date ranges are the norm.

`escapes` gets the same treatment with `customer_id` where `station_id` sits, and `reported_at` where
`created_at` sits.

### 4.5 The exact count is a design problem, not an index problem

`QueryDefects` runs `await defects.CountAsync(ct)` on every request before fetching the page. At 50M rows
with arbitrary filter combinations, that is a full scan of the matching set every single call. **No index
removes it and no cache covers it** — the filter cross-product is too wide for the keys to be reused.

| Option | Client gets | Cost |
| --- | --- | --- |
| Exact count (today) | Total and page count | A full scan of the filtered set, per request |
| `pg_class` estimate | Approximate total | Only valid unfiltered — wrong for every filtered query |
| Fetch `size + 1`, report `hasMore` | No total, no page count | The UI loses "page 5 of 120" |
| Keyset paging on `(created_at, id)` | Stable pages under concurrent writes | No jump-to-page; cursor plumbing through `PagedResponse` |
| **Capped count** | Exact up to a cap, then `"10,000+"` | One bounded subquery; the UI shows a `+` |

**Recommendation: the capped count**, as the smallest change that removes the pathology. Counting inside a
`LIMIT 10001` subquery bounds the work regardless of how many rows match, and "10,000+" is a more honest
thing to show a user than a precise number nobody reads. Offset paging survives, `PagedResponse` gains one
flag, and the frontend changes in one place.

Keyset paging remains the escape hatch `chain-composition.md` §15 always named it as, and the capped count
does not foreclose it.

One related hazard: `Paging.From` clamps page *size* to 100 but does not clamp the page *number*, so a
caller can ask for page 500,000 and get a 50M-row offset scan. Worth bounding in the same step.

### 4.6 Migrations against a large persistent database

`Program.cs` calls `MigrateAsync()` in the development startup block. Against a populated 50M-row table,
a migration that adds a column with a default or builds an index will run at startup and the app will
appear to hang.

This is the same class of trap `chain-composition.md` already records for Keycloak — the realm import
silently keeping the old realm behind a persistent mount. Persistent storage plus automatic startup work
is where that bug lives.

Phase 2 adds columns (§6) and indexes (§4.4) to exactly this table, so the interaction is not theoretical.
Options are to keep automatic migration but never let a heavy operation ride in on it, or to make migration
an explicit command once the dataset exists. **This needs a decision in workstream A**, and it is the one
item in §4 with no recommendation attached, because it depends on how the developer wants the demo loop to
feel.

### 4.7 The migration history is regenerated, not extended

Phase 2's schema changes are exactly the ones incremental migrations handle worst: a required foreign key
on populated tables (`Station.FacilityId`), two more on tables about to hold 25M rows each
(`Defect.FacilityId`, `Escape.FacilityId`), plus attribution columns and a new entity. Decided 2026-09-12:
**delete the existing migrations and generate one fresh initial migration.**

This is the right moment and it will not come again. Nothing depends on the history, the data is
reproducible by the generator, and doing it before anyone else clones the repo is strictly cheaper than
doing it after. It also collapses what were three ordered steps — attribution columns, facility columns,
indexes — into one.

Two scars from `chain-composition.md` apply directly, and both have cost time before:

**`xmin` must be removed from the generated migration by hand.** It is a Postgres *system* column; EF will
emit a `CreateColumn` for it and the migration will fail on apply.
`PersistenceArchitectureTests.No_migration_creates_the_xmin_system_column` catches this, so it is a guard
rather than a landmine — but only if the architecture tests run before the first `aspire run`.

**`temp/db` has to be deleted too.** A fresh initial migration will not apply over a database whose
`__EFMigrationsHistory` remembers the old ones. Since storage is a bind mount under `temp/` (§4.2), this is
a folder deletion — and it pairs with the `temp/keycloak` deletion that §10.9 needs for the realm import
anyway. Both happen once, together, before the first run.

A third is worth re-reading rather than restating: an index `HasFilter` string is opaque to EF, so a
mismatch with the naming convention survives `migrations add` and only fails on apply. §4.4 adds a partial
index, so this is live.

Index adjustments after the measurement run (§4.4) are ordinary incremental migrations from that point on,
or another regeneration while the project is still pre-release — but the one initial migration should be in
place before the generator ever runs.

## 5. Workstream B — edit, delete and reactivation

### 5.1 "Delete" is three different features

The single word covers three requests with different answers.

**Reactivation — the real gap.** Every lookup lifecycle command is one-way: `DecommissionStation`,
`RetireErrorCode` and `DeactivateCustomer` have no inverse. Decommission a station by mistake and there is
no route back through the API. This is a genuine functional hole, it is the smallest of the three, and it
is the one most likely to be what "delete" actually meant. Each is a three-to-five link chain in the exact
shape of the command it reverses, including `ResolveActor` and `RecordDomainEvents`.

**Voiding a fault record.** A defect raised in error is a real event, and the honest shape is a `void` or
`cancel` command carrying an actor and a reason — the same shape as `ResolveDefect`, and a record that
survives an audit. A `DELETE` that removes the row destroys the thing the system exists to keep, and the
outbox event recording the deletion would outlive the record it describes.

**Actual row deletion.** Recommended nowhere. If it is wanted for demo hygiene, that is a generator or
maintenance concern, not an endpoint.

### 5.2 The concurrency token — the blocking decision

Every mutable entity carries `Version`, mapped to Postgres' `xmin`, and `SaveChanges` already converts a
`DbUpdateConcurrencyException` into a 409. That machinery is complete and **entirely untested in practice**,
because `Version` appears in no request and no response anywhere in `Features/`. v1 never contests it: every
write is either a create or a transition that runs once.

Edit changes that on day one. Two users open the same station, both save, and without the token on the wire
the second silently overwrites the first — the 409 never fires, because nothing told EF what version the
client was editing.

| Option | Shape | Note |
| --- | --- | --- |
| Version in the response body and the request body | `Version` on the read model, echoed in the update request | Explicit, obvious in Scalar, no HTTP subtleties |
| `ETag` / `If-Match` headers | The HTTP-native answer | Correct, and composes with the response caching in §8.5; more plumbing, and needs a decision on weak vs strong |
| Nothing — last write wins | No change | Only defensible if edits are rare and single-user, which is a claim about the facility, not about the code |

No recommendation here on purpose: it is a genuine product decision about how the facility works. But it must
be answered before the first edit endpoint, not after, because retrofitting it changes every update
contract at once.

### 5.3 What is editable is not uniform

"Add edit endpoints for all domains" needs enumerating per entity, because three fields resist it:

- **`Code` on Station, ErrorCode and Customer is identity.** Writes bind on codes, not ids
  (`docs/wireframes/README.md` §2), so changing a code re-points every future write while leaving history
  intact. Defensible, but it is a rename with consequences and probably a separate command from editing a
  name.
- **`Severity` is derived, never entered.** It comes from the chosen error code via `ClassifyDefect` /
  `ClassifyEscape`. It cannot appear on an edit form.
- **Changing a Defect's error code is a reclassification**, and therefore re-derives severity. That is a
  link — the existing `ClassifyDefect` — not a field assignment. An edit chain that writes `ErrorCodeId`
  directly and leaves `Severity` stale is the most likely bug in this workstream.

### 5.4 Roles

There is exactly one distinction today: the `admin` policy on the six lookup write endpoints, and plain
`RequireAuthorization()` on the other eleven. Any authenticated user can resolve any defect.

That was fine when every write was additive. Edit and delete make it worth a second look — can a user edit
a fault they did not raise? Can they void one? Not necessarily a new role, but a deliberate answer rather
than an inherited default.

**Workstream F reshapes this ground underneath B**, splitting `admin` into `facility-admin` and `system-admin`
and introducing authorization that depends on the row rather than the route (§10.6). Whatever B decides
about editing a fault someone else raised should be decided knowing that, so the two answers do not end up
using different mechanisms for the same kind of question.

### 5.5 The frontend consequence

`docs/wireframes/README.md` §2 states flatly that there is no edit endpoint, therefore no edit screens, and
**"no pencil icon anywhere in this design."** It also names the lookup edit gap as *known rather than
deliberate*. Workstream B reverses the premise of that section, so it needs rewriting alongside — the
detail pages stop being read-only surfaces with one action, and the lookup tables grow an actions column.

## 6. Workstream C — Escape attribution

### 6.1 What is being reversed

`chain-composition.md` §1 and the Escapes milestone record that an Escape deliberately links to neither a
Station nor a Defect, on the ground that *"the inward trace-back would be unreliable often enough to
mislead, and a nullable field that is usually null is worse than no field."*

That reasoning anticipates the "make it optional" proposal specifically. It is not a strawman, and the
reversal should be made knowing it.

**The counter-argument holds anyway:** when the trace *is* known, discarding it is a real loss, and the
recorded objection is about a field that can pass itself off as fact. That is fixable by construction
rather than by omission.

### 6.2 The safeguards that make it defensible

Three, and the first is most of the value.

**Name it as a claim.** `StationId` reads as truth to everyone who later writes a query.
`SuspectedStationId` or `AttributedStationId` does not. One word, and it is the difference between a chart
titled "defects by station" meaning what it says and meaning "escapes somebody guessed came from here."

**Carry provenance.** A bare nullable FK is a trap: the same column filled by an operator's judgement and by
a batch-record trace mean different things and must not be pooled. A small enum beside the id fixes it.

**Make coverage mandatory in analytics.** Any aggregate over an attribution reports its denominator —
*"attributed for 412 of 3,900 escapes."* A chart over 11% of the data that looks like a chart over the data
is exactly the misleading §1 feared, and this costs one number to prevent. This is a rule for workstream D,
and it is the condition on which the reversal makes sense.

### 6.3 The two links are not equally reliable

Worth separating rather than adding both reflexively.

A link to a specific **Defect** means "we caught this internally and it still reached the customer" — a
containment failure. When it is known at all it is usually known with confidence, because it was found by
going and looking at the defect record. It is also the more valuable of the two analytically.

A link to a **Station** is far more often a guess. And it is partly redundant: a linked defect already
carries its station, with the defect's own reliability attached.

**Recommendation: the Defect link first**, station attribution only if a case appears where the station is
known and the defect is not.

### 6.4 Sequencing

These are new columns on `escapes`, which the generator is about to fill. Adding a nullable column is cheap
metadata; indexing it across tens of millions of rows is not, and neither is backfilling one. **Settle the
shape, then generate** — this is why C sits inside A's window in §3.

The generator should populate attribution at a realistic rate — a minority of escapes, not all and not none
— or every coverage figure in workstream D will read as either 0% or 100% and prove nothing.

### 6.5 Documentation

`chain-composition.md` §1 and the Escapes milestone both record the old decision as settled. When this
lands they need updating in place, with the reversal and its date, in the style §13 uses for the decisions
it revisited. That is a doc edit to make **after** the developer confirms the final shape, not alongside
the proposal.

## 7. Workstream D — analytics and the dashboard

The route and the component already exist: `dashboard-page.tsx` returns an empty fragment, and
`docs/wireframes/README.md` §8 explicitly left the dashboard unwireframed on the grounds that *"no endpoint
aggregates anything"* and that designing it first *"would quietly commit the backend to work nobody has
agreed."* This workstream is that agreement.

### 7.1 Decide the questions before the endpoints

The shape of the API follows from what the page answers. Plausible set:

- Open defects by severity, right now.
- Top error codes over a window.
- Resolution throughput — raised vs. resolved per day, and time-to-resolve.
- Escape trend, and escapes by customer.

**Escape → Defect containment becomes answerable only if workstream C lands**, and then only with the
coverage caveat from §6.2. Until then, no dashboard tile may imply that trace exists.

**Anything phrased as an escape *rate* will read at roughly 50%** against this dataset, because §4.1 puts
escapes at parity with defects for read-path coverage. That is a property of the demo data, not of the
query. Either avoid the rate framing on the dashboard or accept that the numbers are visibly synthetic —
what should not happen is someone reading 50% as a finding.

### 7.2 Endpoint shape

Read chains are single-link query slices — an aggregate endpoint is the same shape, so this needs nothing
new from the kernel.

One `GET /dashboard` returning a composite is fewer round-trips and one cache entry; several endpoints load
independently, fail independently, and let the page render progressively. **Leaning toward several**, on the
grounds that the SPA has no client cache and one slow tile should not hold the page — but this is worth
deciding against the real query timings, not in advance.

### 7.3 Precomputation is not optional at 50M

This is the requirement the dataset creates. A trend over two years of 50M rows cannot be computed per
request at interactive latency, whatever the indexes.

The candidates are a Postgres summary table or materialized view refreshed on a schedule, versus a cached
aggregate. **A summary table is the better default**: it is queryable, joinable, survives restarts, and
composes with the rest of the read side. Caching a computed aggregate in Redis is a way of avoiding a
recomputation that a summary table avoids more durably.

Grain and refresh cadence — hourly rollups, daily, or both — are open, and follow from §7.1.

### 7.4 Time bucketing

`created_at` is a `DateTimeOffset` stored UTC. A facility's "yesterday" is a shift calendar, not a UTC day. Any
bucketed chart needs an explicit answer on the day boundary and whether shifts matter, or the numbers will
disagree with what the floor believes and the dashboard will lose its credibility on first contact.

### 7.5 Charting

No component kit and no chart library are in the project — shadcn/ui was considered and not taken, and
codegen was rejected because generated files conflict in git. The charting decision inherits that context
and has no default. It should be made explicitly, in keeping with the frontend conventions already
recorded in the wireframes README.

## 8. Workstream E — caching

### 8.1 `HybridCache`, and stampede is the reason

`HybridCache` does request coalescing per key: N concurrent callers for a cold key produce one database
query and N−1 waiters. That is the feature worth adopting it for, and hand-writing it correctly is
unpleasant.

**The coalescing is in-process.** It deduplicates within one instance, not across them — at two instances a
cold key means two queries. That is fine, and it means stampede protection is not an argument for Redis.

### 8.2 What is cached

**Stations, error codes and customers** — and `Facility` once workstream F lands, which is the smallest and
most static of them all. Bounded, small, read on nearly every screen, changed almost never.

If §10.4 chooses read scoping, the cached lookups become per-facility for facility admins, so the cache key gains
a facility dimension — still trivially small, but it is a key-shape change worth noticing rather than
discovering.

One key-shape note: cache the **full** list per lookup and filter `IsActive` in memory after the read,
rather than keying on `includeInactive`. It halves the key space and makes invalidation one key per entity
type.

### 8.3 What is not cached, and why

**`GET /defects` and `GET /escapes`.** The cache key is the cross product of station × error code ×
severity × resolved × page × size. Most keys are written once and never read, so nearly every entry pays
serialization and almost none are hit. They are also the tables that change all day, so every create and
resolve invalidates an unknowable set of combinations — realistically a tag purge on every write, which
drives the hit rate toward zero while adding a round-trip in front of a query still being run.

**50M rows makes this worse, not better.** A larger table widens the key space and lowers reuse. The fix for
these endpoints is §4.4 and §4.5 — an indexed query with a bounded count is faster than a cache miss and is
never stale.

`GET /defects/{id}` is a legitimate candidate — one stable key, one invalidation point — but it is not the
load problem, so it is not worth the first invalidation link.

### 8.4 Redis is deferred, and here is the trigger

The scale argument does not reach the cached data. **50M fault rows do not make the station list longer.**
Stations, error codes and customers are dimension tables; they stay small however large the fact tables
grow. A few hundred stations, a few thousand error codes, tens of thousands of customers — all three fully
cached is single-digit megabytes, which fits in L1 with no eviction pressure to relieve. The 50M rows live
in the tables §8.3 says not to cache.

What an L2 costs today: a cross-instance invalidation problem that does not yet exist, a serialization
boundary (and note `HybridCache`'s serializer is independent of the `JsonStringEnumConverter` configured for
HTTP JSON, so `Severity` will be an int in the cache and a string on the wire), and another container that
can be down.

`chain-composition.md` §6 flags the load-bearing unknown: *"`HybridCache` may already do this through its
own back-plane, in which case none of it is hand-written. Confirm that before building it."* **That
confirmation is still outstanding** and must be verified against the pinned package version rather than
assumed in either direction.

The asymmetry is what settles it: `HybridCache`'s call site is identical with and without L2, so adding
Redis later is a registration change, not a rewrite. Waiting is nearly free; building early is not.

| Trigger to add Redis | |
| --- | --- |
| A second API instance actually runs | The real one — cross-instance staleness is the problem L2 solves |
| A demo deliberately shows horizontal scale | Legitimate, and worth naming as the reason rather than dressing it as a performance need |

### 8.5 Two cheaper layers, above the cache

For the lookups specifically, in order of leverage:

**The frontend.** `station-combobox.tsx` fires a `useGet` on every mount, and with TanStack Query removed
there is no client cache at all — opening the new-defect form three times is three round-trips. A
module-level promise cache for the three lookup endpoints eliminates more database calls than the entire
server-side stack, because it eliminates the request.

**HTTP.** `ETag` plus `Cache-Control: private` on the three lookup GETs turns repeat fetches into 304s.
`private`, not `public` — these are authorized responses. This also composes with the `If-Match` option in
§5.2 if that is the direction taken.

Then L1. Then, eventually, Redis.

### 8.6 Invalidation

`chain-composition.md` §6 settles the mechanism: a post-save link that only enqueues, plus a hosted service
that evicts, with the TTL as the backstop. Not the outbox — a poll interval is a window in which a
decommissioned station still reads as active. Nothing here needs inventing, but §9 has to be resolved first.

## 9. The one architecture change phase 2 needs

`chain-composition.md` §6 shows the invalidation shape as an ordinary trailing link:

```csharp
.Link<SaveChanges>()             // commit boundary
.Link<InvalidateStationCache>()  // enqueues only — no Fail path
```

The as-built architecture test disagrees. `ChainArchitectureTests.Nothing_follows_the_saving_link` asserts
that `SaveChanges` is the **last** link, with no exemption, and `CLAUDE.md` states "`SaveChanges` is
terminal" — matching the test rather than the document.

So the first cache-invalidation link turns a green architecture test red. That is a decision, not a
workaround:

| Option | Consequence |
| --- | --- |
| Post-save enqueue-only links become legal | The test needs a way to recognise them — a marker interface is the obvious candidate, and it makes "cannot fail" a type-level claim rather than a review question. §6 already predicted the review-question weakness |
| Invalidation moves out of the chain entirely | Rule 10 stays absolute; the endpoint or a decorator does the enqueue, at the cost of the feature's story no longer reading as one list |
| `.OnCommitted<>()` returns | §14 has this as superseded, and the trigger it names — a post-commit action that must be able to fail — is not what this is |

**Recommendation: the first option**, with a marker interface, because it closes the exact gap §6 admitted
to. Whichever is chosen, `chain-composition.md` §6, `CLAUDE.md` and the architecture test have to end up
saying the same thing — today two of the three agree and the document is the odd one out.

Settle this before the invalidation link is written, not when the test fails.

## 10. Workstream F — Facilities and scoped administration

A facility admin manages the reference data belonging to their own facility; a system admin manages everything.
Stations bind to a facility. This is the largest workstream in phase 2 and the only one that changes how
authorization works.

### 10.1 The names

**`Facility`.** Chosen 2026-09-12 over `Plant`, which was the recommendation. The argument for `Plant` was
that it is already the project's own word — `chain-composition.md` §1 opens with *"logs and tracks quality
faults from a production plant"* — and it was not taken: `Facility` reads better beside Defect, Escape and
Station, and it carries less heavy-industry connotation for a system that may one day cover a site that is
not a production line. `Site` was the other candidate and is vaguer; `Factory` reads informal.

Recorded here so the alternative is not reopened. It does mean `chain-composition.md` §1's prose and the
entity name now use different words for the same thing, which is worth a sentence in that document when it
is next updated.

Structurally it mirrors the lookups it sits beside — `Id`, `Code`, `Name`, `IsActive`, `Version` — so it
inherits the create/list/deactivate shape, the unique code index, the `xmin` token and the actor-on-event
convention without anything new being invented.

**One constraint worth recording before anyone extends this.** `chain-composition.md` §4 bans `Line` as a
name, along with the rest of the MES vocabulary. The natural manufacturing hierarchy is Facility → Line →
Station, and the middle level cannot be spelled that way in this codebase. Not a problem today, since
stations bind directly to facilities, but it will need a different word if a level is ever inserted between
them.

**`facility-admin` and `system-admin`.** The only thing separating the two is scope, so the names say the
scope. This renames the existing `admin` role, which is close to free: adding any role at all means editing
`fhs-realm.json`, and `chain-composition.md` records that the realm import **only runs when the realm does
not already exist** — so `temp/keycloak` has to be deleted for the change to take effect regardless. Do the
rename in the same motion.

The cheaper alternative is to leave `admin` as the unscoped role and add `facility-admin` beside it. It saves
nothing beyond the rename itself and leaves `admin` ambiguous in every policy name that follows.

### 10.2 A role does not say which facility

`facility-admin` describes what someone may do. It says nothing about where, and that assignment has to live
somewhere.

| Option | Note |
| --- | --- |
| **On `Actor`** | Recommended. `Actor` is already the API's own model of who acted, it is the natural place for something the API is authoritative about, and the generator can seed it |
| In a Keycloak claim | Identity-correct in principle, but business data in the realm file — and the realm-import scar makes iterating on it slow and easy to get wrong |

A single `FacilityId` on `Actor` is the right starting point. A join table is the escape hatch if someone
turns out to administer two facilities, and nothing here forecloses it.

### 10.3 Not all three lookups should be scoped alike

The request treats stations, error codes and customers as one group. They are not, and this is the
decision in workstream F most worth getting right.

| Lookup | Scope | Why |
| --- | --- | --- |
| **Station** | **Facility-scoped — settled** | A station is a physical position inside a facility. Unambiguous, and it is the binding the whole workstream was asked for |
| **Error code** | **Open — recommended global** | A taxonomy exists to be comparable. If each facility owns its codes, "which fault is most common across the company" becomes unanswerable, and that is one of the more valuable questions §7 could answer. If facility-local codes are genuinely needed, the shape is shared codes plus additions — a nullable `FacilityId` where null means shared — not a required one |
| **Customer** | **Open — recommended global** | The same customer buys from several facilities. Per-facility customers means duplicate rows for one real company, and escape analytics fragments along a line that does not exist in the business. A facility admin arguably should not own customers at all |

### 10.4 Read scope — settled, and it is the expensive answer

**A facility admin sees only their own facility's defects, escapes and scoped lookups.** Decided
2026-09-12, over the cheaper write-only alternative where a facility admin sees everything and may change
only their own rows.

Three consequences follow, and none of them are optional now.

**It reaches every read slice**, all seven of them, plus every aggregate in §7 and the dashboard. This is
the single largest surface in phase 2.

**`Defect` and `Escape` both need a denormalised `FacilityId`.** Filtering 25M rows by joining through
`stations` is exactly the query shape §4.4 exists to avoid, and the facility predicate will be on *every*
read, not an optional filter. The index set in §4.4 gains a facility leading column on the common paths.
**This is a pre-generation schema decision** — it is why F sits inside A's window in §3.

**The denormalised value is historical truth, not a cache.** If a station is ever reassigned to a different
facility, defects already recorded keep the facility where they actually happened, and that is correct.
Writing it down because it looks precisely like a denormalisation bug, and someone will eventually try to
"fix" it with a trigger.

**Scope belongs to every actor, not only to admins.** If only facility admins are scoped, an ordinary
operator still sees every facility and the restriction is decorative. So `FacilityId` sits on **every**
`Actor` (§10.2), and the two concepts read separately:

| Concept | Governs | Applies to |
| --- | --- | --- |
| The actor's facility | What you can **see** | Everyone except `system-admin` |
| The `facility-admin` role | What you can **change** — your facility's scoped lookups | Only that role |

### 10.5 Facility is inferred, and escapes cannot infer it the same way

**A defect takes its facility from its station.** No create form offers a facility picker — it is derived,
exactly as severity is derived from the chosen error code rather than entered. `LoadAndEnsureStationExistence`
already loads the station, so the derivation is a step in a chain that is nearly there.

**An escape has no station.** `CreateEscape` takes a customer code, an error code and a description; the
absence of a station is the deliberate v1 decision that workstream C is about reversing, and even after C
the attribution is populated for a minority of rows by design. So "inferred from the station" is not
available here at all.

| Candidate source for an escape's facility | Verdict |
| --- | --- |
| **The reporting actor's facility** | **Recommended.** Always populated, needs no new input, and honest — someone at that facility took the complaint and logged it |
| The customer | No. §10.3 keeps customers global precisely because they span facilities |
| The attributed defect (workstream C) | Covers a minority of rows by design. Useful as a refinement, useless as the rule |
| A picker on the create form | Contradicts the decision that facility is never entered |

The asymmetry is deliberate and worth stating plainly: **a defect's facility is where it happened; an
escape's facility is who received it.** Each is the authoritative answer for its own record — a defect
occurs at a physical position, an escape arrives through a person.

**What this means at the two create endpoints, including for a system admin.**

A system admin has no single facility of their own, so both create pages give them a facility control. For
defects that control is **not an input** — a defect's facility comes from its station, so choosing a
facility only *narrows the station list*, and the facility still arrives through the chosen station exactly
as it does for everyone else. `CreateDefectRequest` therefore gains no field at all, and the server logic
is identical for both kinds of user.

Escapes have no station to carry it, so there an admin genuinely has to say. `CreateEscapeRequest` gains an
optional facility code, and the rule is that absent means *derive from the actor* while present requires
`system-admin`.

| | Facility comes from | Admin override | Request change |
| --- | --- | --- | --- |
| **Defect** | The chosen station | Narrows the station list, client-side | **None** |
| **Escape** | The reporting actor | States the facility explicitly | An optional facility code, rejected for non-admins |

The enforcement is one link in both cases even though the sources differ, which is what keeps this from
becoming two separate mechanisms.

### 10.6 The caller's facility is read from `Actor`, never from the request

The SPA needs to know which facility the signed-in user belongs to — it drives the header, the create
pages, and whether a facility switcher is shown at all. That is not in the token: §10.2 puts the assignment
on `Actor`, in the database. Hence **`GET /me`**, called after login.

It is worth building for a second reason. `ResolveActor` fails with `UnknownActor` when no `Actor` row
matches the token's subject, and today the SPA only discovers that when a write fails. Calling `/me`
immediately after login turns a confusing mid-task error into a clear one at the door — which matters more
once seeded demo accounts and realm users have to line up (§10.8).

Shape: a single-link query slice on `FhsQueryDbContext`, like every other read, rather than reusing
`ResolveActor`, which runs on the command context. It costs a small duplicated subject lookup and keeps the
read side uniform. Name the response for the **actor**, not the user — `chain-composition.md` reserves
`User` for `ClaimsPrincipal` — even though the route reads `/me`.

**And the endpoint does not change where authority lives.** `/me` exists so the UI can *show* the facility.
Every write still derives it server-side from the resolved actor, or from the station in the defect case. If
a facility arrived on a request and the API took it at face value, a caller could post into another
facility with a single curl and the entire scoping model would be decorative. The only request field that
may ever carry a facility is the escape's admin override above, and it is checked against the role before
it is used.

### 10.7 A scoped picker is not enforcement

Under read scoping the station combobox will only show the caller's facility, which means the ordinary path
never produces a cross-facility defect. That is a UI convenience, not a rule.

`CreateDefect` still has to reject a station outside the actor's facility, or the constraint lives in the
frontend where it can be bypassed by anyone calling the API directly. So facility enforcement has two
distinct shapes: a check on **create**, comparing the resolved station's facility against the actor's, and
a check on **an existing row** before mutating it. §10.8 is about the second; the first is the same idea one
link earlier.

### 10.8 Authorization stops being declarative

Every v1 endpoint authorizes on the route: `RequireAuthorization()`, or `RequireAuthorization(AdminAccess)`
on the six lookup writes. Facility scope cannot work that way, because whether the caller may proceed depends
on the row being touched, which is not known until it has been loaded.

In Chain Composition that is a **link**, and it fits unusually well — an ordered step between the load and
the mutation, reading as one more line of the feature's story:

```csharp
.Link<ValidateRequest<DecommissionStationRequest>>()
.Link<ResolveActor>()
.Link<LoadAndEnsureStationExistence>()
.Link<EnsureFacilityAccess>()               // new — reads the loaded station, fails 403
.Link<DecommissionStation>()
.Link<RecordDomainEvents>()
.Link<SaveChanges>()
```

It needs a narrow capability interface so the link can be global rather than written per feature — the
State must expose the actor and the facility being touched. `IHasActor` covers half of it already, and
`Actor` gains the assignment from §10.2. Whether the second half is a new capability or an addition to an
existing one is a design question for the step, and `chain-composition.md` §5's "promoted only on second
use" rule applies: the second scoped feature is what proves the interface, not the first.

The route-level policy does not disappear. `system-admin` endpoints — creating a facility, for instance —
stay declarative, because nothing needs loading to know the answer.

### 10.9 What else moves

**Keycloak, and the coupling that makes or breaks a fresh clone.** The realm needs the two new roles and
**3N + 1 users for N facilities** — one system admin, one facility admin per facility, and two operators
per facility. One of each cannot demonstrate a scoping rule, and the facility count multiplies through both
the realm file and the generator's seed, so it is worth fixing early. The scar applies as always: delete
`temp/keycloak` or the edit silently does nothing — which §4.7 needs anyway.

The part that is easy to miss is that **the realm and the generator have to agree on subject ids.**
`ResolveActor` fails the request with `UnknownActor` when no `Actor` row matches the token's subject — it
does not create one. So a Keycloak user with no seeded actor logs in successfully and then errors on every
write, which looks like a broken app rather than a missing row.

The realm already establishes the pattern: its two users carry hand-written fixed GUIDs
(`11111111-1111-4111-8111-111111111111` for `operator`, `22222222-…` for `admin`) rather than
Keycloak-generated ones. Extend it — one `system-admin`, and per facility one `facility-admin` plus an
operator or two, each with a readable fixed GUID — and have the generator seed `Actor` rows with exactly
those `SubjectId` values and the matching `FacilityId`.

**The generator (§4.3).** It seeds facilities, stations bound to them, and the actors above. That is what
makes every environment start from the same reference data, and what lets a demo switch between a facility
admin and a system admin without anyone configuring anything. It is the developer's stated reason for
moving lookups into the generator and it is a good one.

**The frontend.** `use-is-admin.ts` reads one role from the ID token and returns a boolean; it becomes two
roles. Read scoping also means the UI needs a notion of which facility is in view, and a facility switcher
for system admins — who are the only users who can see more than one.

**Existing rows.** `Station.FacilityId` is required, so the migration needs a facility for the stations that
already exist. In a POC with regenerable data this is a one-line backfill, and it is only worth naming
because a required FK on a populated table is the awkward case in general.

Real, and each waiting on something. Listed so they are not rediscovered as surprises.

| Item | Why it is not here | Trigger |

| **The outbox is never drained** | `ProcessedAt` is written by nothing outside the entity and the migrations. The data already exists; it needs a read surface |

| **Search** | No endpoint takes a free-text parameter; filters are exact-match dropdowns bound to unpaged lookup lists. Fine at ten error codes, unpleasant at a few thousand | The same scale point that motivated caching, pointing at a different fix |
| **Sort** | `GET /defects` has a fixed `created_at DESC` sort and no parameter | A column header someone wants to click |
| **Mobile pass** | Wireframe 07 was deferred to a single pass after the reference-data screens, which shipped 2026-09-12 — so this is **due**, and independent of every workstream above | Nothing blocks it |
| **Deployment and CI** | `chain-composition.md` §1 still lists local Kubernetes hosting as the one open item; there is no pipeline in the repo | Anyone other than the developer needing to run this |
| **Notifications** | The classic first outbox subscriber, and the thing that would justify draining it | Pairs with the outbox reader |
| **Attachments** | A photo of the defect is the standard ask for a facility quality system. Real domain gap, no infrastructure for it | A user asking |
| **Frontend architecture convention** | §14 leaves it open — the SPA is organised by component kind, not vertical slice, so the two sides do not share one mental model | A separate document either way |
| **`CreateEscapeEndpoint .cs`** | One file in seventeen has a space in its name | A rename, whenever that folder is touched |
